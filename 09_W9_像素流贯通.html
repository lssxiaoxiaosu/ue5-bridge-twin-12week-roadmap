WEEK 09 ／ 12

像素流贯通：让浏览器打开就是三维场景

本周目标：UE5 打包为独立程序；把 PixelStreamingInfrastructure 的信令服务器跑起来；两台设备的浏览器同时看到三维画面并能操作。

建议工时 22–26 h 学习 : 实做 ≈ 45 : 55 对应条款 第 1、5、7 条（平台形态、性能） 关键前置 W1 的 D5 若已跑通，本周会轻松很多
本周最大的坑：网上多数中文像素流教程已经作废 像素流的前端与 Web 服务器已迁出引擎仓库，改为独立仓库 PixelStreamingInfrastructure，插件名也出现了 Pixel Streaming 2。 任何还在教「直接跑引擎自带 SignallingServer / 老 run.bat」的教程，第 2 步就会卡住。 本周只以官方文档 + 那一个独立仓库为准。
开工前必须确认的一件事（它决定本周工作量） 2–4 人同时看，是「同一视角 + 主持人控制」还是「各自独立漫游」？
已核实：官方 PS2 是「一个 UE 实例 = 一份渲染 = 所有浏览器同一视角」，输入默认共享，官方把这个模式定位为「同一会话、不同控制权限」——即主持人操作、其他人观看。 若要求每人独立视角，则必须「一实例一流」（每实例带 -PixelStreamingID，前端按 streamerId 分配）， 而旧 matchmaker 已于 5.5 弃用，需自建分配服务；且 12 GB 显存跑 2 个实例已属风险区。
这一条没确认，本周可能从「两天」变成「两周」。建议按「同一视角 + 主持人控制」推进，并把这个口径写进方案请甲方确认。

像素流：本周全部依赖这几份

Getting Started with Pixel Streaming ★ 本周首推
Epic 官方已实测·中文可访问必学（逐字对照做）
→ 打开（中文）
为什么这周逐字读：这是当前最准确的部署步骤，关键事实已为你核实出来：
① 插件在 Graphics 分类下，名称可能是 Pixel Streaming 或 Pixel Streaming 2；
② 端口：80 和 8888 需要放行；先关掉本机其他 Web 服务器；
③ 局域网先用 localhost / 127.0.0.1；跨网段或公网需要配 STUN/TURN（peerConnectionOptions）；
④ 编辑器内启动参数：-PixelStreamingURL=ws://127.0.0.1:8888；打包后每个 exe 启动都要带同样参数（做快捷方式）；
⑤ 流程已变更：前端与 Web 服务器改为独立仓库 PixelStreamingInfrastructure。三种获取方式：直接 clone、git clone --branch UEX.Y、或到引擎目录 \Engine\Plugins\Media\PixelStreaming\Resources\WebServers 跑 get_ps_servers 脚本；
⑥ 服务器启动：SignallingWebServer\platform_scripts\cmd\setup.bat → 启动脚本；成功标志是控制台出现 Streamer connected；
⑦ 建议加 -RenderOffScreen：避免窗口被最小化导致输入流中断（生产部署建议加）。

性能与编码（本周必须确认的一件事）

Stat 命令与性能复核（确认是 GPU 编码）
Epic 官方已实测·中文正文复用
→ 打开（中文）
为什么这周再看：开启像素流后，视频编码会额外占用 GPU。你必须在开流状态下重新测帧率—— 很可能「单独跑 UE5 有 35 fps，开流后掉到 26 fps」。
已核实的相关事实：官方称消费级 N 卡的硬件编码器通常上限约 8 个会话，第 9 路起自动切软件编码； 默认的 -PixelStreamingUseMediaCapture 在某些平台上会多耗约 10% CPU。 你的场景是单实例一流，风险不大，但「开流后是否仍 ≥30 fps」必须实测。

筛视频的硬标准：必须讲 PixelStreamingInfrastructure 新架构。若视频里出现「引擎自带的 SignallingServer 目录」「老 run.bat」「matchmaker」—— 说明它讲的是旧流程，直接跳过。

逐日任务（D1–D6）

D1（3–4 h）打包独立程序 + 基本验证

  1. 整理打包配置：
    • 设置默认地图（打包后一启动就是主场景）
    • 确认 Pixel Streaming 插件已启用
    • 检查打包设置：Shipping / Development、包含哪些关卡与资源
  2. 打包到 D:\UE\Build\，双击 exe 确认：
    • 能独立运行（不依赖编辑器）
    • 模型加载正常、帧率达标、交互正常
  3. 做启动快捷方式，Target 追加：-PixelStreamingURL=ws://127.0.0.1:8888 -RenderOffScreen。
    为什么现在就带参数做快捷方式 打包后的 exe 每次启动都要带参数。做个快捷方式（或 .bat）能避免每次手打，也方便 W11 的一键启动脚本。
  • 打包产物能独立运行，性能与编辑器内接近
  • 快捷方式带参数可用

D2（3–4 h）信令服务器：完整走一遍

  1. 克隆正确分支（W1 若已做过，这里核对分支是否与引擎版本匹配）： 
    cd D:\UE\PixelStreaming
git clone --branch UE5.8 https://github.com/EpicGamesExt/PixelStreamingInfrastructure.git
git branch -r          # 核对可用分支：UE5.8=Current / UE5.7=Supported / UE5.6=EOL / master=Dev
  2. 安装依赖并启动： 
    cd PixelStreamingInfrastructure\SignallingWebServer\platform_scripts\cmd
.\setup.bat
.\start.bat
    默认端口：streamer 8888 / player 80 / sfu 8889。若 80 被占用，改配置里的 player_port。
  3. 启动打包程序，观察信令服务器控制台是否出现 Streamer connected。
  4. 本机浏览器打开 http://127.0.0.1 → 点页面 → 点播放 → 看到画面。
  5. 读一遍 Docs/pixel-streaming-2-migration-guide.md，了解 PS2 与旧版差异（避免后面踩老坑）。
  • 信令服务器正常启动，端口监听正常
  • 出现 Streamer connected
  • 本机浏览器能看到并操作画面

D3（3–4 h）局域网多设备接入（2–4 人同时看）

  1. 查本机局域网 IP（ipconfig），例如 192.168.x.x。
  2. 放行防火墙：Windows 防火墙对 80 与 8888 入站放行（这一步不做，别的设备一定连不上）。
  3. 第二台设备（另一台电脑/平板）浏览器访问 http://192.168.x.x → 应能看到同一画面。
  4. 验证多人同时：同时开 2–4 个浏览器（不同设备或同机多窗口），确认：
    • 都能看到画面
    • 帧率与延迟可接受
    • 注意官方行为：所有连接默认共享控制权——如果多人同时拖鼠标会互相打架。这正是「主持人控制」的问题所在
  5. 若需要限制控制权：在播放器页面侧配置输入策略（W10 会做正式版，今天先确认问题存在）。
  • 第二台设备能访问
  • 同时 2–4 个客户端可看
  • 已知悉「控制权共享」的行为并记录

D4（3–4 h）开流后的性能与画质调优

  1. 重测帧率：在开流状态下用 stat fps / stat unit / stat gpu 测——这是验收口径（因为验收就是通过浏览器看的）。
  2. 编码参数调优（查 Reference 页）：
    • 分辨率：1080p 通常够用；投影演示可试 720p 换流畅度
    • 码率：局域网可以高一些，画质更好
    • 确认走的是 GPU 硬件编码而非 CPU 软编（软编会显著增加 CPU 与延迟）
  3. 延迟测量：从「本机操作」到「浏览器画面响应」的主观延迟，用录屏对比帧（同时录桌面与浏览器）估算。记录数值。
  4. 若性能不达标：按 W4 的顺序压画质（Lumen 已关 → 降 ScreenPercentage → 减可见构件）。
  • 开流状态下帧率有实测数据
  • 确认是 GPU 编码
  • 延迟有估算数值（记录方法）

D5（3 h）稳定性与故障处理

  1. 断线重连测试：关掉 UE5 程序再启动 → 浏览器刷新后能否恢复；关掉信令服务器再启动 → 引擎能否重连。
  2. 多客户端掉线测试：关掉其中一个客户端，其他客户端是否受影响。
  3. 写一份《像素流故障速查表》（验收现场会用）：
    现象排查顺序
    浏览器打不开页面信令服务器是否在跑 → 80 端口是否被占 → 防火墙
    页面能开但黑屏是否 Streamer connected → 编码器是否可用 → 显卡驱动
    别的电脑连不上IP 是否写对 → 防火墙放行 → 是否同一网段
    卡顿stat gpu → 码率太高 → 分辨率太高 → 网络
    画面糊码率 → 分辨率 → 编码器设置
  4. 准备演示应急预案：若像素流当天失败，直接双击打包 exe 现场演示（这是你架构上的天然退路，一定要提前演练一次）。
  • 断线重连可用
  • 故障速查表已成文
  • 应急预案（exe 演示）演练过一次

D6（3 h）收尾 + 证据 + 下周排程

  1. 整理证据：两台设备同时观看的录屏、开流后帧率截图、延迟估算记录 → Docs\evidence\W09\。
  2. 更新验收自测表：像素流相关能力可勾选；第 5 条补「开流状态下」的性能证据。
  3. 准备 W10 的前置：确认要给播放器页面加哪些控制（隐藏默认 UI、限制输入、与 Web 后台通信）。
  4. 写 devlog。
