WEEK 05 ／ 12

生成与告警：让构件随数据变色、随异常闪烁

本周目标：用动态材质实例（MID）驱动「正常 / 预警 / 报警 / 紧急」四档阈值着色与闪烁；把告警的三级阈值与状态流转做出来，并实现「告警 ↔ 三维构件位置」双向关联。

建议工时 22–26 h 学习 : 实做 ≈ 40 : 60 对应条款 第 6、20 条（数据联动着色、告警管理） 硬指标 端到端延迟 ≤2 s；告警触发 ≤3 s
本周的知识衔接 你在 W4 做剖切时，可能已经提前摸到了「动态材质实例」——如果没有，本周正式学。 剖切、着色、闪烁三件事用的是同一套机制（材质参数），学一次用三次，这是本路线里性价比最高的一处复用。

核心：动态材质实例（MID）——本周唯一的新技术

虚幻引擎中的实例化材质
Epic 官方已实测·中文正文必学（本周最重要）
→ 打开（中文）
为什么这周看：这是本周全部工作的地基。官方这页正好讲了你需要的每一件事：
① 区分常量材质实例（MIC）与动态材质实例（MID）——只有 MID 能在运行时改参数；
② 蓝图路径：Create Dynamic Material Instance 节点 → 再用 Set Material 应用到构件；
③ 参数类型：标量（Scalar）、向量（Vector，常用于可配置颜色）、纹理、静态参数；
④ 最容易踩的坑（务必记住）：参数必须先在父材质里参数化，否则实例里根本看不到；静态参数在编译时生效、运行时改不了——用错参数类型是「颜色改不动」的第一原因。
官方举例甚至就包含了「改变架构可视化中的漆色」，与你的场景高度对应。

逐日任务（D1–D6）

D1（3–4 h）四档阈值着色（先用手动数据验证逻辑）

为什么先用手动数据 着色逻辑本身与数据来源无关。先用变量手工调值，把「改一个数就变色」验证掉，再接真数据——避免逻辑问题和数据问题纠缠。
  1. 做父材质：给构件材质加一个向量参数（如 BaseColor）与一个标量参数（如 Emissive 用于闪烁），必须先在父材质里参数化。
  2. 做四档配色：正常（绿/灰）、预警（黄）、报警（橙）、紧急（红）。写一个函数：输入测点值 + 三级阈值 → 输出档位 → 设置颜色参数。
  3. 做闪烁：用时间轴或 Timer 让自发光参数在报警/紧急档位下往复变化；预警档不闪烁（避免满屏闪，演示时反而看不清重点）。
  4. 性能注意：5000+ 构件不要每帧都给所有构件创建 MID。只给「可见且需要着色」的构件创建并缓存，其余保持原材质。
  • 手工改变量，构件颜色能按四档变化
  • 报警/紧急档会闪烁，预警档不闪
  • 帧率没有明显下降（stat unit 对比 D1 前后）

D2（3–4 h）按分区取「最不利测点」驱动构件着色

  1. 明确映射规则：一个构件可能关联多个测点（例如一个节段贴多片应变片）。规则建议：
    • 单个测点 → 直接取该测点档位
    • 多个测点 → 取最不利（档位最高的那个）
    • 无测点构件 → 用所属分区的档位或保持默认色
    把规则写进文档——验收时甲方一定会问「这个颜色是根据什么来的」。
  2. 实现映射：用 W2 的测点表（含「所属构件编号」）建一张「构件 → 测点列表」的表；每帧或每 N 秒重算一次档位。
  3. 加图例：界面上固定显示四档色卡与含义（正常/预警/报警/紧急），并标明当前用的是哪个测点。
  • 构件颜色由「其所属测点中最不利的那个」决定
  • 映射规则已成文
  • 界面有四档图例

D3（3–4 h）告警三级 + 状态流转 + 通知

  1. 告警分级：按测点、按指标自定义阈值，≥3 级（预警/报警/紧急）。阈值配置只维护一份（放 Web 侧库表，UE5 订阅）。
  2. 状态流转：未确认 → 已确认 → 已恢复。加操作按钮与操作人记录（对应第 27 条日志审计）。
  3. 触发延迟测量：从「数据到达」到「告警产生」打时间戳，合同要求 ≤3 s。把日志存下来（这是第三方测试报告会要的证据）。
  4. 通知 ≥1 种：声光最简单（界面提示音 + 红色闪烁横幅），邮件/短信需要服务，建议先用声光 + 邮件。
  • 三级阈值可配置且生效
  • 状态可流转，有操作记录
  • 触发延迟有实测数值且 ≤3 s
  • 至少一种通知方式可用

D4（3–4 h）告警 ↔ 三维位置关联 + 点击定位

  1. 告警带构件信息：每条告警必须记录「构件编号」，这是「位置关联」的前提。
  2. 点击定位：点告警条目 → 相机平滑飞到对应构件 + 该构件高亮 + 属性面板弹出（复用 W2 的「定位按钮」与 W4 的 Set View Target with Blend）。
  3. 反向定位：点三维里的构件 → 告警列表滚动到相关条目。双向都能用，验收演示才顺。
  4. 录一段完整的「告警触发 → 点击 → 飞到构件」的演示视频。
  • 告警记录含构件编号
  • 点告警能飞到构件并高亮
  • 点构件能定位到告警条目
  • 演示视频已存证

D5（3–4 h）端到端延迟 ≤2 s：把证据链做出来

这是合同硬指标，且第三方测试报告一定会查 「实测数据从采集到模型显示的端到端延迟 ≤2 秒」——注意是端到端，从采集箱出数据算起，到 UE5 画面变色为止。
  1. 在链路的四个点打时间戳：
    1. 采集箱发出（设备侧时间或报文里的 ts 字段）
    2. Broker 收到（EMQX 日志/Dashboard）
    3. 数据库写入（库表时间戳）
    4. UE5 着色生效（蓝图里打日志 + 屏幕上的时间显示）
  2. 实测并记录：做 20 次以上采样，算最大值（验收看的是最坏情况，不是平均值）。
  3. 若超标，按以下顺序排查：默认刷新周期是否 ≤5 s（合同要求 1–60 s 可配、默认 ≤5 s）→ Broker 与库的往返 → UE5 侧是否在做耗时计算 → 网络。
  4. 归档：把带时间戳的日志存入 Docs\evidence\W05\延迟实测日志\。
  • 四个环节都有时间戳记录
  • ≥20 次采样的最大值 ≤2 s
  • 日志已归档，可复现

D6（3 h）Web 侧对接 + 本周收尾

  1. 统一阈值来源：确认 Web 与 UE5 读的是同一份阈值配置（改一处两边都变）。这是最容易出岔子的地方，本周必须验证一次。
  2. Web 侧补齐告警列表、状态流转、通知设置界面；ECharts 出告警统计图（超限次数、超限时长）。
  3. 更新验收自测表：第 6、20 条应基本达标；第 11、16 条标注进度。
  4. 整理证据包，写 devlog。
