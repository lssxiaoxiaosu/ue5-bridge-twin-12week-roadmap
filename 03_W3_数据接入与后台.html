WEEK 03 ／ 12

数据接入与后台：让真数据第一次走进系统

本周目标：把「采集箱 → Broker → 库 → UE5」这条路打通至少一条通道。同时启动 Web 后台（升级你现有 Three.js 原型），让真数据在库里落下来。

建议工时 22–26 h 学习 : 实做 ≈ 45 : 55 对应条款 第 16、17、21 条（数据管理、协议接入、存储） 风险等级 本周最大不确定性
本周为什么是最大风险周 前面两周的坑都是「自己可控」的（装引擎、导模型）。本周的坑在设备侧：采集箱到底吐什么、点位表在哪、寄存器地址是什么、 主题怎么命名——只要一样卡住，整周就空转。所以本周的策略是：先打通一条最简单的通道，不要一上来就接 130 个测点。
两个已核实的结论，能让你少走弯路 ① MQTT 是引擎自带的——不需要买插件、不需要写 C++。 ② JSON 也是引擎自带的——JsonBlueprintUtilities 提供纯蓝图节点，不需要 VaRest。 这两条把本周的「要采购/要编程」风险直接归零，剩下的纯粹是「对接」问题。

UE 侧：把数据读进来（本周技术主线）

MQTT 插件（引擎内置）
Epic 官方已实测·可访问必学（本周核心）零成本
→ 打开（插件索引页）
为什么这周看：这是你接真数据的官方免费通道。已核实要点：
① 插件位置 Engine\Plugins\Protocols\MQTT\MQTT.uplugin，编辑器里在 IOT 分类下，标 Experimental；
② 核心类 UMQTTClientObject（蓝图显示名可能是「MQTT Client」），提供 Connect / Disconnect / Subscribe / Publish / Unsubscribe， 并带 OnConnect / OnMessage / OnPublish 委托；
③ 连接 URL 形如 Mqtt://user:pass@host:1883，走 TCP 1883 / 8883（不是 WebSocket）；
④ 它依赖 Json Blueprint Utilities（所以两者天生配套）。
⚠️ 诚实提醒：该插件索引页没有蓝图节点清单，具体节点要从 API/Plugins/MQTTCore 下逐个查。这意味着你需要一点探索时间， 但已有开发者用它做出完整项目，路径是通的。
JsonBlueprintUtilities（蓝图 JSON 库）
Epic 官方已实测·可访问必学零成本
→ 打开（API 页）
为什么这周看：MQTT 收到的消息是 JSON 字符串，要靠它转成结构体。已核实的节点名（可直接在蓝图里搜）： Load Json from String、Load Json from File、Save Json to File、Get Json String、 Get Field、Set Field、Has Field、Get Field Names、Convert Struct To Json String。
推荐链路：MQTT OnMessage → Load Json from String → Get Field（输出直接挂到结构体）→ 驱动 W5 的着色。
⚠️ 需你自己验收的一点：Get Field 对「多层嵌套数组 → 结构体」的自动化程度，本文档无法替你确认。 建议第 1 天就花半天做个小实验验证；若确实吃力，再考虑 VaRest 兜底（但先别买）。
HTTP 请求（蓝图）—— 本周作为兜底通道
未验证兜底用
为什么放这：如果 MQTT 插件在你的 EMQX 配置下出问题，可用 HTTP 轮询顶上（配合 Timer）。 但本文档未能找到并验证一个名为「HttpBlueprint」的官方页面——请不要按这个名字去引用或写进方案。 蓝图里搜 Http 看实际有哪些节点，以你引擎里实际存在的为准。
关键限制（已核实）：UE 没有蓝图可用的内置 WebSocket（IWebSocket 仅 C++）。 所以「实时」只能靠 MQTT；HTTP 轮询只适合 1–5 s 级刷新，不要用它去做「端到端延迟 ≤2 s」的验收通道。

逐日任务（D1–D6）

D1（3–4 h）先摸清设备，再写代码

顺序不能反 很多人这周先埋头学 MQTT，学到一半发现设备根本不给数据。先验证数据源存在，再学怎么接。
  1. 拿到设备的三个关键文档（找第 3 项负责人/设备厂商）：
    • 点位表：每个测点的编码、类型、单位、量程、寄存器地址或主题名
    • 协议说明：Modbus TCP 还是 MQTT？端口？是否主动推送？推送频率？
    • 数据格式样例：要一段真实的报文样本（JSON 或寄存器值），这比任何文档都有用
  2. 用工具先看到数据（不写一行代码）：
    • MQTT 路线 → 用 MQTTX 或 EMQX Dashboard 的 WebSocket 客户端订阅，看能不能收到报文
    • Modbus TCP 路线 → 用 Modbus Poll（试用）或 QModMaster（开源）读寄存器
  3. 把测点表落成 CSV：至少先落 30 个测点（合同要求 ≥30 个绑定），字段建议： 
    测点编码 / 测点名称 / 指标类型 / 单位 / 量程下限 / 量程上限
预警阈值 / 报警阈值 / 紧急阈值 / 所属构件编号 / 分区
    产物：D:\UE\Docs\测点表.csv（这份表后面 UE5 与 Web 两边都要用）。
  • 拿到了点位表 / 协议说明 / 报文样例（或明确知道缺哪一份、找谁要）
  • 用工具亲眼看到至少一条真实数据
  • 测点表.csv 至少 30 行

D2（3–4 h）Broker 落地 + 数据落库

  1. 装并跑起 Broker：EMQX（Docker 最快）或 Mosquitto（最轻）。验证：本机用 MQTTX 能发布/订阅。
  2. 设计主题（Topic）结构——这一步现在花 30 分钟，后面省几小时。建议： 
    bridge/{桥名}/sensor/{测点编码}/data      ← 数据
bridge/{桥名}/sensor/{测点编码}/status    ← 在线状态
bridge/{桥名}/cmd/ue5                     ← Web → UE5 指令（W10 用）
bridge/{桥名}/state/ue5                   ← UE5 → Web 状态回报（W10 用）
    为什么现在就把 cmd / state 主题定下来 W10 要做「Web 里点测点 → UE5 相机飞过去」。如果主题结构到时候再改，两边的订阅全要返工。
  3. 数据落库：先用最简单的方案（PostgreSQL 普通表即可），把报文写进去。时序库选型放到 W6，不要本周纠结。 验证：库里能 select 出真实数据行。
  4. 接一个「数据服务」（Node.js，与你现有 demo 技术栈一致）：订阅 MQTT → 写库；同时提供 REST / WebSocket 给前端。
  • Broker 跑起来，能发布/订阅
  • 主题结构已定并写进文档
  • 数据库里能查到真实数据行

D3（4 h）UE 侧接通路：用假数据先打通蓝图链路

为什么要先用假数据 设备侧的联调时间不可控。先用假数据把「UE 侧能收到消息并解析」这件事验证掉， 等设备通了只需换主题名，避免两边问题纠缠在一起。
  1. 启用 MQTT 插件（IOT 分类）与 Json Blueprint Utilities，重启编辑器。
  2. 用 MQTTX 往你设计的主题手工发一条 JSON 报文，例如： 
    {"tag":"SG-01-05","type":"strain","value":842.5,"unit":"με","ts":1758700000}
  3. UE 里用 MQTT Client 节点连接 Mqtt://127.0.0.1:1883 → 订阅该主题 → 在 OnMessage 里 Load Json from String → Get Field → 取值并 Print String。
  4. 把取到的值存进变量（如 当前测点值）——W2 已经在属性面板留好了这个占位字段，接上就能看到数字跳动。
  • UE 能连上 Broker 并订阅成功
  • 收到手工发的报文，能解析出数值并打印
  • 属性面板的「实时数据」字段能跳动了
卡住时查什么 「连不上」→ 先用 MQTTX 在同一台机器验证 Broker 正常，再排查 UE 侧 URL 格式（Mqtt:// 大小写、端口、是否要账号密码）　｜　 「收到但解析不出」→ 把原始字符串先 Print String 出来看，确认是不是 JSON、有没有 BOM/转义问题　｜　 「插件启用后编译报错」→ 检查引擎版本与插件兼容性，重启编辑器

D4（3–4 h）切到真数据源

  1. 把 D3 验证好的蓝图链路的主题名/地址换成设备真实值。
  2. 同时接 Web 侧：数据服务订阅同一主题并落库，前端页面能显示这条真实数据。
  3. 处理两个必然出现的问题：
    • 断线重连：网络抖动时不要让系统静默失效——加状态标志 + 界面上显示「连接中/已断开」
    • 数据异常：真实传感器会有跳变、空值、超量程。本周只需记录原始值，预处理规则放到 W6
  4. 记录第一条真实数据的证据：截图 + 时间戳，存入 Docs\evidence\W03\。
  • 真数据从采集箱一路走到 UE5 画面
  • 断线时界面有提示，恢复后能自动重连
  • 证据已归档

D5（3–4 h）Web 后台起步：跑通并接管现有原型

  1. 把 系统demo 在本地跑起来（必须通过 HTTP 访问，直接双击 index.html 会因 file:// 下的 ES Module / fetch 限制加载不了模型）。
  2. 按 W3 资料区的方法通读 README.md → js/data.js → js/app.js，画出它现有的模块关系图（手画即可）。
  3. 做一个最小改造：把它的仿真数据源替换成 D4 的真实数据接口（先只替换 1 个测点，验证链路）。
  4. 把仿真引擎保留为可切换选项——验收当天的备份方案。
  • 原型在本地能正常跑（三维模型能加载）
  • 能说出它的数据层/视图层/主控三部分如何交互
  • 至少 1 个测点走的是真数据

D6（3 h）收尾：稳定性 + 证据 + 下周排程

  1. 做一次「关掉设备再打开」的测试，确认系统能自愈。把过程录屏。
  2. 整理证据：真实数据截图、库中数据行、UE 面板跳动的录屏。
  3. 更新验收自测表：第 17 条（协议接入）可勾选大部分；第 16、21 条标注进度。
  4. 写 devlog，明确 W4 的第一件事（剖切与测量）。
