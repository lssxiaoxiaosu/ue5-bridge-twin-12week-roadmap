本周用法：33.3 ms 是 30 fps 的总预算，先看 stat unit 四项数值（Frame / Game / Draw / GPU）判断瓶颈在哪一项，再对症下药：
瓶颈项典型原因（你的场景）处理

可视性与遮挡剔除（Draw 线程的救命页）
Epic 官方已实测·中文正文必用
→ 打开（中文）
本周用法：桥梁构件被桥面遮挡的部分不该被渲染。用 r.VisualizeOccludedPrimitives 1 看哪些本该被剔除、 stat initviews 看剔除效率、FreezeRendering 冻住画面后自由走动检查遮挡关系。
官方明确指出的关键点：「可见静态网格体元素」是对渲染线程影响最大的因素——对你有 5000+ 构件的场景，这是最该优化的方向。
Lumen 性能指南 + TSR + VSM（三个画质换帧率的旋钮）
Epic 官方已实测·中文正文按需查
→ Lumen 性能指南　 → TSR　 → VSM
本周用法：这三个是 GPU 侧最有效的降本手段，但要注意它们的观感代价：
  • Lumen 关闭（你的既定策略）→ 用烘焙静态光照 + SSAO/DFAO 替代。桥梁是静态结构，观感损失很小
  • TSR + r.ScreenPercentage 60–70 → 最划算的一档；再低会出现明显模糊，投影演示时会被看出来
  • VSM → 你的构件是静态的，VSM 可以留；但若场景里有移动光源，缓存失效会很贵，检查一遍
做「演示档」和「验收档」两套设置：验收档保证面片 ≤200 万时 ≥30 fps；演示档在投影时可以再降一档求流畅。

逐日任务（D1–D6）

D1（4 h）性能专项：按 33.3 ms 预算逐项压实

本周最关键的一天 合同第 5 条是硬指标，且 W4 测的是「单独跑 UE5」，现在必须测「开流 + 数据联动 + 回放」的复合状态—— 这才是验收现场的真实负载。
  1. 建立基准：在最终形态下（像素流开启 + 实时数据 + 看板联动）测一轮，记录 Frame / Game / Draw / GPU 四项数值。
  2. 按瓶颈逐项处理（照 D1 资料的表格对症下药）。每次只改一项，改完复测，否则你不知道是哪项生效了。
  3. 重点处理 Game 线程（这是最容易被忽略的）：
    • 把所有 Tick 里的周期逻辑改为定时器（按刷新周期跑，而不是每帧）
    • 着色更新只处理值变化的构件
    • MID 缓存复用，不要重复 Create
    • 拾取保持节流（W2 已做）
  4. 做两套画质档：验收档（保证达标）与演示档（投影用）。一键切换。
  5. 出最终性能证据：
    • 截图：stat fps + stat rhi（含面片数）+ stat unit（四项时间）
    • 录屏：旋转 / 缩放 / 平移三种操作各 10 秒（合同明确写的是这三种操作下的帧率）
    • 开流状态下的浏览器录屏（证明验收口径下达标）
    存入 Docs\evidence\27条验收\C05_性能_*.{png,mp4}
  • 知道瓶颈在哪一项并已针对性优化
  • 有两套画质档可一键切换
  • 面片 ≤200 万时 ≥30 fps（开流状态下，有截图与三种操作的录屏）
  • 首次加载 ≤30 s 复测达标

D2（3–4 h）系统设置：逐条核对第 22–27 条

D3（3–4 h）第 9、10 条：BIM 轻量化证明（本周最可能翻车的一条）

这两条一直被推到本周，现在必须处理 合同第 9 条：原始模型 ≥200 MB 时，轻量化后 ≤原始 30%（压缩率 ≥70%），保留属性 ≥10 项。 第 10 条：≤300 MB 模型轻量化解析 ≤60 s，轻量化场景加载 ≤30 s。
难点在于「轻量化产物」的定义——用 Datasmith + Nanite 路线时，什么算「轻量化后的数据量」？
  1. 先明确定义并写进方案。可选口径：
    • 口径 A：打包后资产体积（.pak / Content 大小）÷ 原始模型文件体积
    • 口径 B：导入后工程内该资产的字节数 ÷ 原始体积
    • 口径 C：轻量化处理工具的输出文件体积 ÷ 输入文件体积
    建议用口径 A 或 B（可现场用文件管理器复核，最没有争议），并在方案里写明计算方式。
  2. 实测并留证：
    • 原始模型体积（字节）
    • 轻量化后体积（字节）
    • 压缩率 = 1 − 后/前
    • 解析耗时（秒）与场景加载耗时（秒）
    做成《轻量化体积对比表》，存 Docs\evidence\27条验收\C09-C10_轻量化_体积对比表.xlsx
  3. 若压缩率达不到 70%，可选手段：
    • 降低 Tessellation 等级（W1 已验证有效）
    • 用 Proxy Geometry 减面（官方推荐用于 Datasmith 结果）
    • 剔除不可见构件（内部结构、重复几何）
    • 评估 IFC 路线是否体积更小
    • 若确实做不到：如实记录并立即上报，讨论是否调整口径或采用第三方轻量化工具——这是需要提前沟通的事，不能拖到验收
  4. 属性保留 ≥10 项：核对构件属性面板能读出的字段数（编号、名称、类别、材质、规格、节段序号、面片数、坐标、族名、类型名……），确保 ≥10 项且可查询。
  • 轻量化口径已定义并写入方案
  • 体积对比表已出（含压缩率与耗时）
  • 属性保留 ≥10 项且可查询
  • 若不达标，已上报并形成处置方案

D4（3–4 h）一键启动脚本（现场演示的保命符）

为什么必须有这个 你的全套系统要同时跑：MQTT Broker + 时序库 + 数据服务 + Web 后台 + 信令服务器 + UE5 程序。 验收现场你要在 2 分钟内让它们全部起来，而不是逐个双击、逐个排错。
  1. 写一个启动脚本（.bat 或 .ps1），按顺序启动并做健康检查：
    1. 启动 Broker → 检查端口 1883
    2. 启动数据库 → 检查端口
    3. 启动数据服务 → 检查 HTTP 健康接口
    4. 启动 Web 后台 → 检查端口
    5. 启动信令服务器 → 检查 8888 / 80
    6. 启动 UE5 打包程序（带 -PixelStreamingURL 参数）
    7. 最后打印一行「全部就绪，请打开 http://... 」
  2. 写一个停止脚本（同样重要——演示完要能干净退出，避免端口占用影响下次）。
  3. 做开机自启（可选但推荐）：把服务注册为 Windows 服务或用启动文件夹，避免现场忘记启动某项。
  4. 演练 3 次：每次从「全部关闭」状态冷启动到「可演示」，记录耗时。目标 ≤2 分钟。
  • 一键启动 / 停止脚本可用
  • 冷启动到可演示 ≤2 分钟（实测 3 次）
  • 脚本包含健康检查与就绪提示
